这是一个面向薄壁件加工与在线检测场景的**双五轴镜像测厚闭环 + 多传感器融合控制系统**。系统两侧机构隔着薄壁工件协同运动：加工/测量侧负责姿态与测厚，支撑侧负责跟随和接触力控制，同时结合超声、电涡流、压力、水压和线激光等信息，把测量结果转换成受约束的补偿量反馈给设备。

我在项目中的定位是**系统研发工程师，参与跨模块联调、软件开发与算法分析**。我的工作不是只做超声数据处理，而是覆盖了从坐标变换、运动学、传感器融合、状态估计和补偿控制，到通信协议、C++/Qt 上位机、线程时序、安全保护和问题定位的一整条工程链。

项目中对外使用的两个主要精度口径是：**壁厚补偿精度 ±0.05 mm、测厚精度 ±0.01 mm**。这些属于项目/团队结果；我负责和参与的是其中的跨模块联调、软件与算法分析工作。

## 一页看懂系统

整个系统可以理解成五类感知信息围绕双五轴运动形成闭环：

- **超声回波**：给出主厚度测量；
- **四路电涡流**：估计探头与工件表面的相对法向；
- **轴向压力**：判断支撑头接触力是否合适；
- **水压**：判断超声耦合状态和当前测量是否可信；
- **线激光**：生成表面轮廓点云，用于扫描、标定、位置预估和碰撞边界。

数据进入系统后，不是直接把某一个传感器值送给执行机构，而是经过**坐标统一 → 运动学映射 → 质量判断 → 状态估计 / 多传感器融合 → 受限补偿控制 → 安全状态机**再作用到设备。

## 1. 坐标系、齐次变换与线激光点云

系统中同时存在**工件坐标系、设备坐标系、末端执行器坐标系、TCP、线激光坐标系、各传感器坐标系以及安装偏置**。不同传感器看到的量必须先转换到统一的设备/补偿坐标中，才能参与后面的姿态和位置补偿。

基础变换使用旋转矩阵、欧拉角和齐次变换：

`T = [ R  p ; 0  1 ]`

逆变换中的平移项不是简单的 `-p`，而是 `-Rᵀp`：先把平移撤掉，再把向量旋转回原坐标系。项目中的主要旋转姿态落到设备 A/C 两个旋转轴上。

### 线激光扫描链

线激光先通过标定得到相机与激光平面的几何关系，再把图像中的激光线像素反投影为三维点云；点云经过坐标变换统一到设备坐标系，之后用于表面轮廓、几何拟合和补偿量计算。

这条链路可以概括为：

**像素激光线 → 标定模型 → 3D 点云 → 传感器坐标 → 设备/工件坐标 → 表面轮廓与补偿信息**

线激光不是超声测厚主链的一部分，它更偏向**扫描测量、几何标定、预估位置和碰撞边界**。点云/曲面拟合得到的表面法向还会进一步影响刀具或测头姿态；刀路光顺则控制相邻刀位之间的曲率和速度变化。

## 2. 双五轴运动学、逆解、多解与 RTCP

### 正运动学 FK

正运动学解决的是“已知各轴位置，末端现在在哪里”。系统建模使用旋量/逐级变换的思路，把直线轴、旋转轴以及固定安装偏置统一到同一条变换链中，再逐级相乘得到末端位姿。

这套 FK 建模不是我独立推导的，但我参与了使用、联调和代码分析，能够把数学模型与实际轴序、坐标方向和程序实现对应起来。

### 逆运动学 IK

逆运动学反过来解决“目标 TCP 位姿确定后，各轴应该到哪里”。后处理会按照设备实际轴序、方向和安装偏置，把 CAM/目标位姿解析成 `X / Y / Z / A / C`。

其中刀轴方向 `(Nx, Ny, Nz)` 到 A/C 角的核心关系可以写成：

`A = acos(Nz)`

`C = -atan2(Nx, Ny)`

真实工程里比公式更重要的是**多解和连续性处理**。我实际处理过：

- 周期角的等价解；
- `atan2` 象限判断；
- 角度展开与跨 ±180° 连续；
- 按上一拍姿态选择最近解；
- 不可达判断；
- A/C 等轴的机械限位与约 ±370° 保护。

### RTCP

RTCP 的核心是**刀尖点保持**：旋转轴改变姿态时，同时补偿直线轴，使 TCP 相对工件仍保持在目标位置。对这套双五轴设备来说，它把“姿态变化”和“实际加工/测量点位置”绑定在同一条几何链里。

## 3. 电涡流法向、压力 W 轴与水压质量门

### 四路电涡流估计工件法向

四路电涡流传感器按约 90° 分布在测头周围，量程约 0–10 mm。它们不负责测厚，而是判断**超声探头当前应该朝哪个方向**。

两组相对传感器可以先估算两个正交倾角：

`α = arctan((l1 - l3) / 2R)`

`β = arctan((l2 - l4) / 2R)`

更一般的做法是把四个测点拟合为平面 `z = ax + by + c`，通过最小二乘得到平面法向。目标法向随后进入坐标变换和逆运动学，转换为旋转轴与直线轴的姿态补偿。

### 压力传感器与 W 轴

支撑侧通过应变式压力传感器测量接触力，可近似理解为对电压信号做比例和零偏标定得到压力值。

压力太小，支撑不足、振动增加；压力太大，又可能使薄壁件变形或划伤。因此系统设置独立 **W 轴**沿支撑头轴向做小范围快速修正，把“大范围位置随动”和“局部接触力调节”分开。

### 水压作为耦合质量门

水压不是厚度本身，而是超声耦合状态的代理量。水压异常时，即使当前厚度数值看起来没有变化，也不能默认它仍可信，因为可能出现旧值、错误峰或耦合失效。因此水压会参与测量质量判断，在异常时降低可信度或阻断补偿。

## 4. 多传感器融合与状态估计

### D-S 证据理论 + 动态权重

项目使用过 **D-S 证据理论与动态权重**处理不同传感器之间的不确定性和冲突，我与同事共同参与了这部分工作。项目口径中，融合方案相对单一传感器的精度提升约 **25%**。

D-S 可以简单理解为：每个传感器先给出自己的置信度/BPA，再用 Dempster 规则合成多路证据；动态权重则根据当前传感器可靠性实时调整贡献大小。

在工程实现上，我更倾向于把它理解成明确的因果分工，而不是把所有量硬混成一个数：

**超声回答厚度，电涡流回答姿态，压力回答接触安全，水压回答测量质量。**

### 一维 Kalman 与异常门

连续厚度估计使用一维 Kalman，包括状态预测、协方差传播、Kalman 增益和基于 Q/R 的观测融合，同时结合创新残差和质量门拒绝异常数据。

这里我重点处理过一个工程边界：**滤波更平滑，不等于测量精度自动更高。** 无效值、突变、超时和缺测必须在进入补偿前被明确处理；缺测时也不能一直沿用上一拍补偿量。

## 5. PID、补偿控制、MPC 与机电耦合

### 受约束的增量式 PID

厚度误差进入补偿控制后，不是直接无限制修正，而是经过一套工程保护：

**误差 → 死区 → 参数渐入 → 变速积分 → 增量式 PID → 单步限幅 → 总补偿限幅 → 设备执行**

异常情况下系统还会进入**保持、降速、抬刀**等状态。

我参与过生产代码中的 **W1 抬刀、补偿初始化、板卡报警、最大下刀限制**等逻辑，也处理和分析过抗积分饱和、微分滤波、死区、迟滞和限幅等保护项。

PID 调参不是单独追求某一个指标，而是在**上升时间、超调、稳态误差、振荡、噪声放大和系统延迟**之间做折中。

### 多体动力学、MPC 与前馈补偿

项目还进行了机电耦合的多体动力学建模、MPC 和多轴前馈补偿，我参与的是联调和软件/算法分析部分。

- **ADAMS**：建立床身、立柱、滑台等多体模型，并用弹簧阻尼表达部分间隙与柔性；
- **Simulink**：建立位置环、速度环、电流环等伺服模型；
- **MPC**：基于机电耦合模型预测未来误差，在约束下滚动优化，只执行当前第一步，下一周期重新预测；
- **前馈补偿**：针对旋转轴和直线轴动态响应速度不同造成的协同误差，提前加入补偿。

这部分的价值是把“几何上应该同步”进一步推进到“动态响应上也尽量同步”。

## 6. 通信协议与 C++/Qt 上位机

### 64 字节固定协议

我处理过项目中的固定 **64B 通信协议**，包括：

- 字段偏移；
- 大小端/字节序；
- 有符号数；
- 定点编码；
- 固定长度累计接收；
- TCP 拆包、粘包和跨 `recv` 缓存。

接收端按 `2B header + 62B body` 累计出完整帧，而不是假设一次 `recv()` 就一定拿到整帧。当前 P01 这套生产 64B 协议**没有实现 CRC**，这一点和“通用协议里可以有 CRC”分开描述。

我也能够从工程角度区分 TCP 和串口：TCP 更关注连接、流式消息边界、延迟和断连；串口则更关注波特率、校验位、帧同步和读写时序。

### C++/Qt 软件分层

上位机是基于 **C++ / Qt / Windows** 的测试与控制软件，我参与的链路可以按五个模块理解：

1. **采集模块**：通过 DPL 板卡读取 A 扫回波，每个测量值维护时间戳、序号和质量状态；
2. **协议模块**：完成 64B 固定帧组帧、解析和跨读取缓存；
3. **估计模块**：一维 Kalman + 质量门，拒绝无效、突变和缺测数据进入补偿；
4. **控制模块**：把补偿量映射到设备变量，并处理保持、降速、抬刀和防过切；
5. **显示与日志**：实时界面、报警提示以及按程序名组织的 CSV 实验记录。

软件结构上使用模块化分层，把采集、计算、控制和 UI 尽量解耦；多线程使用 `QThread + Worker`、`moveToThread()` 和跨线程信号槽/QueuedConnection；定时主要依赖 `QTimer` / 事件循环和部分高精度计时逻辑。

这里我明确把 Windows + Qt 定义为**软实时**，而不是硬实时。真正需要验证的是周期分布、P95/P99 长尾、CPU 占用和异常情况下的响应，而不是只看平均周期。

资源管理方面，工程中使用 RAII / 智能指针思路管理句柄和缓冲区，并按依赖关系逆序释放资源。
